# Multica 版本协作

日常版本开发由 [feipi-session-browser 项目](https://multica.ai/iampkuhz/projects/96581b13-b676-4be1-a291-b8b5d6aa5097) 管理。Codex 处理建卡、查卡或派发时加载 `feipi-multica-manage-tasks`，用官方 CLI 核实工作区和项目。后台沿用注入任务身份；交互式会话用已授权的工作区。只有讨论或查询时不写平台。

## 一版一分支，一个固定开发目录

- 每版创建 `codex/vX.Y.Z-development`。版本汇总卡记录精确分支，并指向项目 Resources 的固定本机目录（`in_place`）。卡片和评论不复制机器路径，也不靠描述变更执行目录。
- 同版所有子 Issue 在该目录和版本分支上串行处理。不为每张卡另开分支或 worktree。需独立验证或并行隔离时，先确认起点、范围、回收目标和清理条件；不自行切分支、覆盖差异或清空缓存。
- 派发前核对项目目录、daemon、Agent 和活动 Run；开工前再次核对实际 Git 根、分支和继承差异。目录或分支不符、同一 checkout 有冲突写入时，回复 `BLOCKED` 及预期和实际值，不退回 `main`。Run 完成不是验收，也不授予目录独占权。
- 每个版本第一次提交保留经授权且验证通过的开发基线。后续提交也需明确授权；版本分支不是发布分支，合并、推送、打 tag 和正式发布仍按 [发行流程](../release/README.md)。

## 两种 Issue

| 类型 | 标题与正文 |
| --- | --- |
| 版本汇总卡 | `Feipi Session Browser vX.Y.Z｜研发与交付汇总`。记录开发分支、固定目录资源和一句版本目标；核心改动每项一句，详情按同序补充影响，必要时写发布影响或待决事项。 |
| 子 Issue | 对应一个可独立验收的交付目标，挂到版本汇总卡下。Description 只写长期目标、范围和不做什么；不要把首轮修复的要求写进正文。 |

用户可以直接在 Codex 说问题，无需编号。先在当前版本下查同范围子卡，有则复用，无则创建；只登记时回报卡号与范围，不启动 Agent。相同范围的下一轮开新评论，对其中一轮的补充回复该评论；交付目标变了才新开子卡。不要在父卡直接触发修复。

## 每轮修复：评论登记，明确开工才派发

1. 首轮和后续轮都在子卡评论里写 **现象／复现、期望、验收**。只登记用 `/note`，不提及 Agent；不粘贴真实会话、凭据或运行数据。
2. 用户明确要求开工后，回复该轮需求评论。在 Multica 的 `@` 候选中选择项目工程执行 Agent（本项目当前为 `session-browser-agent`），CLI 用平台核实的 Agent UUID；不粘贴普通文本、不加 `/note`、不重复触发。单轮 Run 不依赖给整卡设置常驻 Assignee。
3. 看触发预览，再以对应评论的 Run 回执确认是否启动；已有冲突 Run 或别的执行者在写时不重复发送。Agent 在触发线程中回填改动、验证和剩余问题，不把 Run 终态当作验收，不自行宣布已发布。
