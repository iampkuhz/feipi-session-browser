# 分层修复反馈闭环

本约定由当前宿主 Agent 执行，不是新调度器。沿用原生测试、现有 Gate/receipt 和任务评论；不另建 registry、循环 runner 或必须先登记才能编辑的状态令牌。

## 每组问题的最小记录

在已有 tasks、笔记或任务评论中保留：失败现象/预期、根因假设与范围、最小复现命令、修复范围、单点与相关结果、对应输入与日志、剩余问题/下一动作。相同根因造成多项失败可归组；必须有共用故障证据，不能仅凭错误数量或同一个 Gate 名称认定同源。

## 选择与流转

| 环节 | 进入与选择 | 失败后的去向 | 通过证明与下一步 |
|---|---|---|---|
| 复现 | 先读当前失败日志，固定症状和预期；优先原有最小用例，无覆盖才补合成测试或可重复检查 | 不能复现则核对输入、fixture、环境，不能先猜改源码 | 留下修前失败依据，再作有边界修复 |
| 单点反馈 | 每次修复后重跑同一个原失败用例；Java 用 --tests，Playwright 用 spec + --grep，Python 用路径 + -k | 返回本根因诊断；不重跑整套，也不只看退出码 | 原症状消失且期望行为被断言，未降低断言/绕开路径，再进入相关回归 |
| 相关回归 | 根据实际消费者选择模块、共享组件、调用方和交互边界；不是扫描整个脏工作区 | 新回归回到单点；共同环境故障先修环境；独立失败单列并判断交付影响 | 相关结果有效且 required 无 skipped/warning，才准备最终交付 |
| 最终交付 | 问题收敛、写入已停止、输入稳定后，运行整个工作区 python3 scripts/gates/cli.py run --mode incremental，不传 selector/base | 按当前 receipt 的失败步骤与日志归组，回到复现/单点/相关环节；Gate 失败不直接结束任务 | 最终 required 全部 PASS 才能宣称验证通过；Done 仍由用户/项目验收决定 |

具体原生命令见 docs/development/README.md 的日常小改。改动触及格式、注释或静态规则时，先选精确路径或所属模块/source set 的原生静态检查，再跑原失败单点；Java `test --tests` 不承接源码质量规则，Python `ruff check` 不承接格式。不要无条件扫描整个脏工作区，也不新增包装器或把 root check 当局部反馈。
局部 green、测试数量下降或修改了文件都不是交付凭证；最终 Gate 承接的 Java 根 check 不重复跑。原生 UP-TO-DATE/FROM-CACHE 不称重跑。

## 进展与停止

- 有效进展是：相同原症状的新修复被确认、排除一个有证据的根因假设、或取得能改变下一动作的新诊断证据。仅换说法、改无关文件、重复相同命令、把错误藏起来不算进展。
- 有进展就继续，累计修复轮数不设两次上限。连续两轮面对相同失败签名、相同输入且没有新修复或证据时，先改变诊断方法/缩小复现；只有替代方法亦无安全可行动作时，才报告无进展阻塞。有进展则该连续计数重新开始。
- 真实外部阻塞包括缺权限/输入、必须由另一工作者停止的冲突写入、受控环境不可用。先完成安全可做的诊断和有依据的替代方案；不能因“范围外”“环境缺失”几个字停止所有可推进工作，也不能越权安装依赖或覆盖他人改动。
- 阻塞报告必须包含原失败、已试方案及证据、仍可自行处理的事项、精确外部条件/责任人、保留的改动与恢复入口。只写“Gate 未通过”不够。
- 使用宿主持久目标时遵守其 blocked 审计阈值；本规则不能提前改写宿主状态。

## 根因和证据边界

区分产品/断言回归、fixture/共同环境、配置漂移、Gate 自身问题、输入变化。静态 JS HTTP 500 应先查资源响应、MIME、服务日志和分发产物，不能把整套交互断言逐条改掉。

证据对应当时命令、源码/依赖、fixture、工具环境和输入；任何相关输入变化使证据失效。不能拿单个文件哈希证明全部依赖未变。优先让原生工具判定复用；未知则重跑受影响范围。最终稳定输入由 Gate 比较，变化期间的 FAIL 凭证只供诊断。停止当前任务写入不代表其他聊天/进程停止；核对具体来源，不新增 writer lease，不自动回滚或清理。

共享 checkout 的修复前范围/继承差异核对、交付前实际写入探测及最终说明沿用[开发手册](../../../../docs/development/README.md#共享-checkout-的实际写入边界)，不另建记录系统。输入漂移先看 `inputValidation.changedPaths`；重采样读取失败看 `unavailablePaths`，无法确定路径时不猜测。保留失效 receipt 的原结果/指纹和日志，再诊断对应路径或公共资源；不得把原步骤绿当有效交付。交付区分本 Run hunk、继承差异、验证范围和剩余责任。

## Run、Issue 与依赖

平台故障重试的 max_attempts 不是内部修复轮次预算；Run completed 只表示本次执行结束。默认依赖放行必须读前置 Issue 的实际验收状态与验证证据，不依据 Run 结束、队列顺序或无异常退出擅自绕过。用户明确授权前一 Run 终态后继续（包括前项 blocked/in_review）时按授权范围推进，保留前项失败与剩余责任；没有该授权则说明未满足的依赖并安全结束。此行为约定不是平台硬依赖锁，不宣称已实现自动依赖调度或目录独占。
