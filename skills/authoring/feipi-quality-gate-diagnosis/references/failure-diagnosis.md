# 失败定位

修复流转、进展和停止条件以[分层反馈闭环](repair-loop.md)为真源。本页只补充取证，不另设重试或必跑检查。

1. 记录原命令、非敏感参数、exit code、当前 receipt 与对应完整 stdout/stderr 的日志路径；不复制 token 或环境变量值，不把大日志贴进上下文。
2. 从本次 receipt 的 Gate/recipeStep/原生任务定位实际失败对象，再读其直接相关代码。不要从过期静态清单猜检查入口。
3. 区分产品/断言、fixture/共同环境、配置、Gate 自身和输入变化。多个失败只有共享故障证据才归组；先确认资源或服务故障，避免逐项改交互断言。
4. 对环境缺口先核查受管工具链、错误覆盖和已有依赖；在已授权范围内采取有依据的替代办法。不越权安装、更改个人配置或权限，但不能仅因一条命令不可用就放弃全部可做工作。
5. Gate 自身误报必须补正常与真正失败的合成覆盖，不删有效质量要求。fixture 只能使用最小合成数据，不能引入真实 session。

工具的 FAIL/BLOCKED 是验证结论，宿主是否停止由共享闭环及宿主规则决定。子任务越界时返回精确缺口，由 main 评估承接，不把 allowed scope 直接解释为整体任务不可继续。
